## 0. Intent
- **Claim** — The public MCP tells an AI assistant about 58 hand-written features (file last edited 2026-06-19) and 20 generic industry pages, while the product has 410 registered screens, 52 industry verticals and 28 website country markets. Assistants cannot find or correctly describe HelloGrowthCRM for most of what it does, and part of what it says is wrong (INR 1,099, "Unlimited users", Free tasks 500, USD $13).
- **Mechanism** — One **publication predicate** (§0c) used by every handler of both new tool families: a record is served only after a recorded, founder-approved decision, default closed. **Every positive capability claim in either family is a reference to one catalogue entry**, so approving a vertical can never publish a capability that has no approved entry. Plus country-aware pricing wording reconciled across both pricing tools, and a check that runs over the complete served responses. Four draft PRs implement a first slice (#94 Free tasks value, #95 catalogue, #96 industry tools, #97 market scope); this plan governs them and **requires #95/#96/#97 to be rebuilt to it** while they stay draft.
- **Observable** — `features_list` returns the 58 legacy entries plus only publishable catalogue entries; `industries_list_modules` / `industries_get_modules` return only publishable verticals whose referenced capabilities are all publishable; legacy package flags and CRM-plan entitlement are separate, separately named fields; both pricing tools agree and state that pricing is country-aware; no record presents a gated, off-by-default, industry-only, plan-unconfirmed or planned-only capability as generally available.
- **Risk** — A public machine-readable surface is repeated verbatim by AI assistants. Over-claiming (super-admin-only, industry-only, TEST-only or not built) is worse than silence. Mitigations: default-closed publication under one tested predicate, capability references instead of free-text positive claims, frozen schemas, banned-claim and structure checks on the served output, planned-not-built items excluded.

## 0c. The publication predicate and the decision record
**One executable, pure predicate in `src/lib/publish.ts`, used by every handler (features list/get, industries list/get, entitlement lists):**
```
publishable(r, registry, now, context) :=
      r.decision ∈ {approved, on_request}
  ∧   r.revoked_on = null
  ∧   r.public_wording_ok = true             // one attestation covering EVERY served free-text field of the record
  ∧   isoDate(r.decided_on) ∧ isoDate(r.verified_at)
  ∧   r.verified_at ≤ today(now, UTC) + 1 day                // clock injected; +1 day absorbs IST vs UTC
  ∧   age(r.verified_at, now) ≤ 90 days                       // stale ⇒ NOT served (closes the gate); never reddens the build
  ∧   r.decision_ref ≠ ""
  ∧   scope rule:  r.scope = "prod"     ⇒ r.decision = "approved"
                   r.scope = "gated"    ⇒ r.decision = "on_request"
                   r.scope = "industry" ⇒ r.industry_key set, and r is publishable only when context.industry_key = r.industry_key
  ∧   (r.decision = "on_request" ⇒ some tier of r.crm_entitlement = "on_request")
  ∧   r is a catalogue entry
        ∨ ( r is a vertical
            ∧ ∀ c ∈ r.capabilities : publishable(c, …, context = {industry_key: r.key or its alias target})
            ∧ (r.kind = "alias" ⇒ publishable(target(r)))
            ∧ alias chain length 1, no cycle, no self-alias )
```
- **`restriction` is derived, never typed:** scope `gated` or decision `on_request` → "Available on request"; scope `industry` → "Only for <industry name> workspaces"; both can apply. It is projected on the record **and** carried per capability inside any vertical that references it. A capability scoped to one industry is never served as applicable to another vertical; an `approved` record cannot have scope `gated`.
- **Integrity at load (startup failure):** duplicate `slug`/`key`/alias/`decision_ref`; a record whose `decision_ref` has no decision; a vertical referencing a missing capability slug; a missing alias target; a self-alias; an invalid `scope` or `crm_entitlement` value; a tier `"on_request"` under `approved`. **Suppression (not startup failure):** any record failing the dynamic clauses (date, age, revoked, wording, context).
- `pending`, `excluded`, revoked, stale, or out-of-context: **not served**; `features_get` / `industries_get_modules` return the same error text as an unknown identifier. Unpublished records are indistinguishable from unknown — no count of them is served.
- **Legacy entries (the 58)** have no decision record. They are outside this mechanism and outside the verification guarantee, reported as such (`catalogue.legacy_verified:false`, and the audit says so). Withdrawing one is an ordinary PR; migrating them to decision records is a separate plan.

**Decision record — three contracts, never conflated:**
| Contract | Holds |
|---|---|
| Repository source (public-safe; `src/data/decisions.ts` and the data files) | `decision_ref` (opaque), `decision` (`pending` default · `approved` · `on_request` · `excluded`), `decided_on`, `verified_at`, `scope` (`prod` · `gated` · `industry`) + `industry_key` when industry, `crm_entitlement` (`{free, growth, enterprise}` each `true | false | "on_request" | null`), `public_wording_ok`, `revoked_on`. **Never:** approver, flag names, product revision, evidence paths, tenant identifiers, founder notes |
| Private workbook (founder-held, sheet *Decisions*, joined by `decision_ref`) | approver, product repo paths and whether each exists on `app`, flag names, hellocrm revision verified against, production deployment/migration/plan restrictions, the buyer cohort the approval attests to, notes |
| Served projection (§0d) | only the §0d keys; never `decision_ref` or anything from the other two rows |
**How approval is made binding:** `src/data/decisions.ts` is owned by CODEOWNERS (the founder). The founder's GitHub review on the exact commit is the approval record. Human setting changes this relies on, **listed as preconditions and read by the weekly audit (AC-18):** branch protection on `main` with require-code-owner-review, dismiss-stale-reviews and no admin bypass; the PR author is not the founder (an author cannot approve their own PR). The PR description lists the `decision_ref`s changed.
**Invalidation and revocation:** nothing detects a product change; only record age is machine-checked. A change to a capability's flag, plan gate or migration, or its removal, is handled by the founder (owner of correction and revocation) flipping the record to `revoked`/`excluded` through a PR, the next business day after being told; the content disappears when 0001's release path deploys that PR. **Until then the capability stays advertised: the window is manual notification plus release time, unbounded while 0001 is blocked.** Age 90 days closes the gate automatically; the audit warns at 45 and routes its message to the founder through the existing `weekly-mcp-audit` task.

## 8. Risks and edge cases
- **TEST ≠ PROD (Q0).** The gate is the founder's recorded decision attesting to a defined buyer cohort (private record), not a super-admin demonstration; no tenant identifier is ever served.
- **Entitlement.** `null` means unknown; `on_request` is served and labelled; an assistant may still drop a qualifier — the limit is in the first sentence of `availability_note` where it exists.
- **The check proves less than a title suggests.** `check:served` catches banned phrases, schema, date, size, publication-state and capability-reference violations; it cannot find a new kind of over-claim or tell a truthful `not_built` sentence from a claim — each record's wording is reviewed by the founder when deciding.
- **Staleness and withdrawal.** Age closes the gate after 90 days; nothing else detects a product change. A capability disabled in the product stays advertised until the founder's revocation PR is deployed through 0001's path — **detection + release time**, bounded by the audit cadence (weekly) and the founder's next-business-day response; age fails at 90 days. Entitlement changes and rollbacks are not detected faster than that.
- **Public repo.** Approver identity, evidence paths, flag names, product revisions and cohort notes stay in the private workbook; git history holds only the public-safe fields and opaque `decision_ref`s (AC-16). A reviewer relies on the founder's GitHub review; no sheet checksum is used.
- **Money claims.** AC-05 certifies consistency, not correctness; each UNCONFIRMED cell has an owner (founder), a public treatment (unchanged, `synced_at` visible) and a decision question (Q2/Q2b). A yearly-discount statement is limited to what the rows show.
- **Locale and currency.** The six local-currency rows come from the 2026-08-06 mirror; no USD annual figure is added to `market_scope`.
- **Alias confusion / chains.** One-level aliases only; chains and cycles fail the load.
- **Payload size and abuse.** Character and byte ceilings are proxies for a token budget; the in-process limiter is per instance; no estate-wide limit is claimed. Static responses still use compute and egress.
- **Enum consumers.** Eight new `category` values can break an exhaustive switch on the old seven (CHANGELOG, AC-14).
- **Tenant-data boundary.** No Supabase service-role credentials, CRM lookups or request-derived tenant context may enter these tools; enforced by an import-boundary check and a network-disabled handler test (AC-19), not by grep alone.
- **Residual: approved wording can be edited later.** `decisions.ts` is under CODEOWNERS but the claim text lives in other files; until CODEOWNERS also covers `capability-catalogue.ts` and `industry-modules.ts` (a human repository setting, listed for the founder), a later PR could reword an approved record without renewed approval. Astra r4 asked for a digest binding instead; not adopted (§10).
- **Assistant answer quality is unmeasured.** A before/after prompt test is registered, not built.
